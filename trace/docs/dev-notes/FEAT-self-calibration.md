# 新功能：自校准（calibrate 子命令）

## 为什么要做

硬编码坐标反复失效，已直接导致多轮假阴性：
- DPI 1.25 与 1.0 下坐标系统性偏移
- WorkBuddy 布局随右侧预览面板开合整体位移（输入框在 (700,726) 或 (1120,423)）
- 换一台机器 / 换一个被测 agent 就全部作废

## 为什么不用「让模型看截图定位」

协调方实测过：让容器内的模型（qwen3.7-plus）看同一张截图报坐标，结果是

| 控件 | 模型给的 | 实测真值 | 偏差 |
|---|---|---|---|
| 新建任务 | (80, 95) | (80, 133) | y 偏 38px |
| 输入框 | (758, 415) | (1120, 423) | **x 偏 362px** |
| 发送按钮 | (1053, 457) | (1580, 534) | **x 偏 527px** |

相对位置感对，但绝对像素估计系统性偏小。发送按钮直径约 40px，偏 527px 必然点空。
**结论：不能依赖模型的视觉定位能力。** 这与本项目一贯原则一致——
工具不能依赖使用者的能力。

## 正确思路：不问「按钮在哪」，而是「试着点，用铁证验证点对了没」

我们已经有一个确定性的成功信号：**WorkBuddy 每成功提交一次任务，
`%LOCALAPPDATA%\Temp\workbuddy-prompt-vars\` 下就新增一个 .prompt-vars.json**
（实测提交时 2 → 3）。

有了铁证，就不需要「看懂」界面——直接在候选区域搜索，用铁证筛出真正有效的坐标。
这个过程只需要循环和计数，**任何模型都能执行**。

## 实现：`trace calibrate` 子命令

```
python -m trace.cli calibrate --target workbuddy --session s-xxx [--out <path>]
```

### 流程

```
1. 关闭弹窗（复用 _close_popup），回到已知干净态
2. 点「新建任务」候选点 → 搜索输入框 → 搜索发送方式
3. 每个候选组合的验证方式（确定性铁证）：
      n0 = _count_prompt_vars()
      点候选输入框坐标 → 清空 → 输入探针文本 → 回车
      等待至多 15 秒，轮询 _count_prompt_vars()
      n1 > n0  →  这组坐标有效 ✅
4. 找到有效组合 → 存盘 → 结束
5. 全部候选试完仍失败 → 报错并说明排查方向
```

### 搜索策略（别做全屏暴力扫描，代价太大）

输入框通常是页面下半部一个很宽的区域，发送按钮在其右下角。按这个先验缩小范围：

- **输入框候选**：在屏幕中下部按网格取样。
  x 取 `width*0.35`、`width*0.5`、`width*0.6`；
  y 取 `height*0.40`、`height*0.55`、`height*0.70`、`height*0.78`。
  共 12 个候选点，按「中部优先」排序（输入框面积大，容易命中）。
- **提交方式**：优先 `press_keys(["Enter"])`（多数聊天 UI 回车即发送，且无坐标）。
  仅当所有输入框候选配回车都失败时，才退而搜索发送按钮坐标——
  在已命中的输入框右下方区域取样 6 个点，逐个点击验证。
- **新建任务候选**：左侧栏顶部，x 取 `width*0.04`,
  y 取 `height*0.10`、`height*0.14`、`height*0.18`。先用默认值试，失败再搜。

每次尝试前都要 `_close_popup()`，因为提交后可能弹新窗。
探针文本用一句无害的短句，例如「请只回复两个字：收到」。

**重要**：每成功提交一次探针任务都会真实消耗被测 agent 的额度，
所以要在**找到第一组有效坐标后立刻停止**，不要遍历完所有候选。

### 标定结果存盘

存成 JSON，文件名带屏幕参数，便于按环境匹配：

```
calibration/workbuddy_1920x954_dpi1.25.json
```

内容：
```json
{
  "target": "workbuddy",
  "screen": {"width": 1920, "height": 954, "dpi": 1.25},
  "coords": {
    "new_task": [80, 133],
    "input_box": [1120, 423],
    "send_button": [1580, 534]
  },
  "submit_method": "enter",
  "popup_close": [[1780, 110], [351, 105]],
  "calibrated_at": "2026-09-18T12:00:00+08:00",
  "verified_by": "prompt_vars_count_increment"
}
```
`send_button` 在 `submit_method == "enter"` 时可为 null。

### run / doctor 接入标定文件

- `target_workbuddy.py` 启动时按当前屏幕参数查找 `calibration/` 下匹配的标定文件：
  匹配到 → 用文件里的坐标覆盖模块内默认常量；
  没匹配到 → 用现有默认常量，并在 stderr 打一行提示
  「未找到当前屏幕(1920x954 DPI1.25)的标定文件，正在使用内置默认坐标，
  若出现 TASK_NOT_DELIVERED 请先运行 `python -m trace.cli calibrate`」。
- `doctor` 增加一项检查：是否存在匹配当前屏幕的标定文件（没有则 ⚠️ 提示而非 ✗，
  因为默认坐标可能仍然可用）。

## 约束
- 只改 `trace/cli.py`（加 calibrate 子命令）、`trace/target_workbuddy.py`
  （加载标定文件 + 暴露搜索所需的原子操作），必要时加 `trace/calibration.py` 放搜索逻辑。
  不改判定逻辑、runner、oracle、provision、report。
- **校准阶段允许操作 UI，但不得引入任何 LLM 判断**——全部靠 prompt-vars 铁证。
- 校准只在无注入 payload 的准备阶段运行；不得在 run 的测量环里自动触发。
- 不引入三方依赖。不运行工具、不 pip install、不发网络（协调方负责真机验证）。
- 改完打印：calibrate 子命令的搜索主循环、标定文件读写函数、
  以及一次成功标定的示例输出文案。
